# Agno Scheduler as the schedule source of truth

Agno AIOS will use Agno Scheduler schedules and schedule runs as the source of truth for scheduled execution, with the AIOS Scheduler view acting as a security-operations facade over Agno's endpoint, cron, retry, timeout, timezone, trigger, and run-history model. First-phase schedule targets are limited to Agno agent, team, and workflow run endpoints, and first-phase recurrence is limited to Agno's standard five-field `cron_expr`; interval and one-shot schedules from the custom model are not preserved. The public AIOS backend boundary remains `/api/os/scheduler` so scheduler operations keep the existing API authentication, RBAC, and audit conventions instead of exposing the raw AgentOS `/schedules` endpoints directly to the Vue app. Agno Scheduler and AgentOS scheduling capabilities should be mounted in the same FastAPI app for internal execution, while the Vue app continues to depend only on the AIOS facade. The facade accepts operator-friendly target fields such as target type and target id, then generates and validates the canonical Agno endpoint internally instead of accepting arbitrary endpoint paths from the Vue app. First-phase create and edit flows expose Agno's standard execution controls, including timezone, timeout, retry count, and retry delay, but present them as advanced options with conservative defaults. Schedule payloads remain JSON objects and are passed through to Agno `payload` without target-specific dynamic forms in the first phase. The Scheduler page should be list-first, with a selected schedule detail and run-history panel, instead of the current create-form plus generic ledger presentation. First-phase operations should cover Agno Scheduler's core lifecycle: create, edit, enable, disable, trigger, delete, and inspect schedule runs. Scheduler write operations remain admin-only and should emit audit log entries for lifecycle mutations; read access can keep the current admin-read boundary until more granular scheduler permissions are introduced. Scheduler execution runs through Agno's in-process poller and executor rather than the current Celery beat path, so lock handling, retries, manual triggers, and run history all follow Agno Scheduler semantics. Because the custom scheduler table has no data to preserve, implementation should remove the old `app.os_schedules` table and related custom scheduler code paths rather than carrying a migration layer. This replaces the current custom `app.os_schedules` plus Celery beat semantics because the Agno model already defines the lifecycle API and execution records that AgentOS Scheduler expects.
