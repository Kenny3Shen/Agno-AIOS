Architecture Review

Agno-AIOS module depth candidates

本报告基于现有 CONTEXT、ADR 约束、CodeGraph 线索和代码体积热点，寻找值得深化的 module。目标不是提出最终接口，而是判断哪里能用更 deep 的 module 提升 leverage、locality 和测试表面。

约束

ADR-0001 保持单 PostgreSQL 数据库并按 schema 划分；ADR-0002 保持 FastMCP 挂载在 FastAPI 的 /mcp/；ADR-0003 确认后端权限检查是安全 seam，前端权限只是 UX。

因此候选项都不重开这些决策，而是在现有控制面、Security Operations Assistant、Chat Session、Trace、Knowledge Base 和 MCP Service 语义内寻找更 deep 的 module。

推荐先看

首选 Trace Workbench state module。它对应 3,293 行单文件视图，现有 store 删除后不会带走足够 implementation，且测试已经表现出源文本断言倾向。深化这个 module 的收益集中在 frontend locality、可测性和日常导航效率上。

1. Trace Workbench state module

Files: frontend/src/components/Trace.vue, frontend/src/stores/traces.ts

Strong

Problem

Trace.vue 体积达到 3,293 行，组合了 Chat Session 过滤、Run 行派生、Trace 加载、Span detail shaping、shell event、debounced refresh 和 drawer geometry。现有 useTraceStore 更像 shallow 状态容器，删除它不会把核心 implementation 一起带走。

Solution

建立一个 Trace Workbench state module，让视图依赖一个更小的 interface；把 Trace/Run/Span 的选择、刷新、派生状态和适配逻辑留在 module implementation 内。这里先不定义具体 interface 形状。

Benefits

locality 更强，Trace Workbench 的规则可以独立测试；视图从复杂状态编排转向展示；未来 Trace 数据结构或 filter 行为变化时，影响面更小。

Before

flowchart TD
  A[Trace.vue 3293 LOC]
  A --> B[Session filters]
  A --> C[Run row derivation]
  A --> D[Trace loading]
  A --> E[Span detail shaping]
  A --> F[Shell events]
  A --> G[Debounced refresh]
  A --> H[Drawer geometry]
  S[useTraceStore shallow] -. refs .-> A

After

flowchart TD
  V[Trace view]
  M[Trace Workbench module]
  I[Small interface]
  AD[Tracing and Session adapters]
  M --> I --> V
  AD --> M
  M --> R[Selection, refresh, summaries, details]

2. Chat Session persistence module

Files: api/services/llm_service.py, api/routes/chat.py, api/services/os_control_service.py

Strong

Problem

llm_service.py 同时承担 Agent Run runtime 和 Chat Session persistence：archive DDL、SQL projection、owner checks、audit、Agno runs 解析、preview 逻辑都在同一个 module 内。删除 session helpers 会把这些规则散落到 route 和控制视图，说明当前 seam 不够 deep。

Solution

把 Chat Session persistence 作为独立 module：它拥有 Session 元数据、owner visibility、archive 状态、Run projection 和 preview 的 implementation。route 和控制面只通过稳定 interface 使用它。

Benefits

后端权限 seam 更容易审查，Chat Session 行为可以脱离 Agent runtime 测试；当前源文本断言可以替换为对 module interface 的行为测试。

Before

flowchart LR
  R[chat route] --> L[llm_service.py]
  O[os_control_service] --> L
  L --> A[Agent Run runtime]
  L --> S[Session SQL]
  L --> P[Owner and archive policy]
  L --> G[Agno runs parsing]
  L --> V[Preview shaping]

After

flowchart LR
  R[chat route] --> C[Chat Session module]
  O[control view] --> C
  C --> DB[(PostgreSQL app/agno schemas)]
  C --> P[Owner, archive, preview, Run projection]
  R --> X[Run runtime module]

3. Security Operations Assistant Run runtime module

Files: api/services/llm_service.py, api/routes/chat.py

Strong

Problem

stream_chat_with_agent 创建 model、MCPTools、Skills、Knowledge Base、Agno DB、fallback Agent，并解析事件流。Run runtime 的 seam 贴近具体 adapter，导致测试 fallback、knowledge filters、provider block handling 时需要碰到太多外部 implementation。

Solution

形成 Security Operations Assistant Run runtime module，把 Run 生命周期和 provider/MCP/Skill/Knowledge adapter 编排集中在一个 deep implementation 里，route 只表达用户意图和权限上下文。

Benefits

运行时故障路径可测，adapter 替换成本下降；Chat route 不再暴露 Agno 组装细节，Run runtime 与 Chat Session persistence 也能拥有清晰 locality。

  participant LLM as llm_service.py
  participant M as Model
  participant MCP as MCPTools
  participant K as Knowledge
  participant DB as Agno DB
  Route->>LLM: stream
  LLM->>M: create
  LLM->>MCP: create
  LLM->>K: create/filter
  LLM->>DB: connect
  LLM-->>Route: event chunks

After

sequenceDiagram
  participant Route as chat route
  participant Run as Run runtime module
  participant A as Adapters

  Route->>Run: requested Run
  Run->>A: assemble model/MCP/Skill/Knowledge
  Run->>Agno: execute
  Run-->>Route: normalized events

4. Knowledge Base runtime module

Files: api/services/knowledge_service.py, api/routes/knowledge.py

Strong

Problem

knowledge_service.py 超过 1,000 行，混合 env config、torch/model loading、embedder/reranker adapter、reader、Agno Knowledge construction、owner filtering、CRUD、search/status。module 的 interface 面积大，implementation locality 弱。

Solution

深化 Knowledge Base runtime module，让 Knowledge Document ownership、chunk metadata、model loading、PgVector filter 和 Agno calls 留在 module implementation 内；route 只处理请求、响应和后端权限上下文。

Benefits

ingestion、visibility 和 search 可通过单一测试表面验证；模型加载和存储 adapter 可替换，减少测试中 patch 全局状态、torch 或 storage 的需求。

  K --> E[env config]
  K --> T[torch/model loading]
  K --> R[readers]
  K --> V[PgVector]
  K --> O[owner filters]
  K --> C[CRUD]
  K --> S[search/status]
  Route[knowledge route] --> K

After

flowchart TD
  Route[knowledge route] --> KB[Knowledge Base runtime module]
  KB --> D[Document and ownership rules]
  KB --> I[Ingestion implementation]
  KB --> Q[Search implementation]
  KB --> AD[Model, reader, storage adapters]

5. MCP runtime config application module

Files: api/routes/mcp.py, api/mcp/server.py, api/mcp/config.py

Strong

Problem

MCP route module 现在承担 config mutation、restart policy、manifest validation、duplicate checks 和 audit shape。runtime 有 refresh seam，但 route 返回 restart_required: true，调用者需要推断 effect。

Solution

在 ADR-0002 的约束内建立 MCP runtime config application module，集中处理 MCP Service 配置写入和 runtime application。route 只表达控制面动作和权限。

Benefits

service toggle、Hi-Agent add/update/delete、upload、runtime refresh 可以通过一个 module interface 测试；MCP Token 和 runtime config 的一致性也更容易纳入同一 locality。

Before

flowchart LR
  Route[mcp route]
  Route --> Mut[config mutation]
  Route --> Val[validation]
  Route --> Dup[duplicate checks]
  Route --> Aud[audit shape]
  Route -. restart_required .-> Runtime[MCP runtime refresh]

After

flowchart LR
  Route[mcp route] --> App[MCP runtime config module]
  App --> Store[config store]
  App --> Runtime[MCP runtime refresh]
  App --> Audit[audit result]
  Runtime --> FastAPI[FastMCP mounted at /mcp/]

6. Shell Navigation and Workspace module

Files: frontend/src/App.vue, frontend/src/components/Settings.vue, frontend/src/stores/shell.ts, frontend/src/stores/sessions.ts

Worth exploring

Problem

App.vue 同时拥有 shell module、nav registry、permission mapper、module host、session sidebar、model chip、theme 和 event bridge。删除现有 store 不会集中复杂 implementation，说明它们仍然偏 shallow。

Solution

探索 Shell Navigation and Workspace module，把 visible nav、active module、permission gating、settings tags、canvas mode 和 session workspace 规则集中起来。这个候选可能需要先确认产品语义再深化。

Benefits

UI shell 行为可以离开源文本断言，转向 module interface 行为测试；导航规则、权限显示和工作区切换拥有更清晰 locality。

Before

flowchart TD
  A[App.vue 1105 LOC]
  A --> N[nav registry]
  A --> P[permission mapper]
  A --> H[module host]
  A --> S[session sidebar]
  A --> M[model chip]
  A --> T[theme]
  A --> E[event bridge]
  Store[shallow stores] -. refs .-> A

After

flowchart TD
  View[Shell view] --> WS[Shell Navigation and Workspace module]
  WS --> Nav[Navigation rules]
  WS --> Perm[Permission gating]
  WS --> Space[Workspace and session rules]
  WS --> Settings[Settings tags]

下一步

建议从一个 Strong 候选开始做追问式设计：先确认 module 的责任、删除测试、真实 seam 与 adapter 数量，再决定是否进入 ADR 或实现计划。当前报告刻意不提出详细 interface，避免过早锁定 implementation。
